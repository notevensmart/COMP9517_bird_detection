### E36 follow-up: raw proposal SET stable; order-only instability causes cap-induced selection changes

[Successful E36 detailed run 43830191020](https://github.com/notevensmart/COMP9517_bird_detection/actions/runs/43830191020) distinguishes candidate coordinates from order. For two original VAL photographs, the **complete uncapped Selective Search coordinate sets were identical** (order-invariant SHA256 sorted lexicographically matched across separate extraction calls). Output arrays were NOT in identical order, even when repeating `cv2.setRNGSeed(42)` and `cv2.setNumThreads(1)`. Image `beach_bird_1379.jpg` has **1508** image-only candidate boxes, and first-1200 capped *sets* changed between calls: hash of sorted first1200 candidates differed. Image `beach_bird_1389.jpg` has **511** total candidates, so while its order changes, the *complete selected set* remains constant. Repeating the RBF on identical feature banks is bit-exact. 

**Diagnosis:** The detector's `selective_boxes` procedure retains Selective Search's unstable returned order and slices `boxes[:1200]`, which changes the candidate set when proposals exceed the cap. This is directly relevant to apparent cross-run AP variability; the raw proposal algorithm itself did not change the full candidate coordinate set on these two diagnostics. A deterministic image-only ranking+cap strategy (e.g., score+spatial/scale quotas with deterministic tie breaks, measured against official VAL AP) would address this, but **must be separately validated** because rank policy itself changes the detector. Simply re-seeding OpenCV did not fix it. E33 frozen run was already launched with the original method, so its single test pass will be reported transparently as a stochastic-order realization; TEST must not be used to select/fit a new deterministic ranking algorithm.


### E36 repeatability audit — previously hidden Selective Search cap nondeterminism (16 Nov 2026)

[First repeatability run 43829427539](https://github.com/notevensmart/COMP9517_bird_detection/actions/runs/43829427539) and [extended run 43830191020](https://github.com/notevensmart/COMP9517_bird_detection/actions/runs/43830191020) inspected actual OpenCV Selective Search results on identical VAL images. **The raw uncapped proposal SET is the same** across repeated calls, including seeded and single-threaded calls, but OpenCV's output **ORDER changes** (even with a fixed OpenCV RNG seed and one thread). The old `src/selective_search_detection.py::selective_boxes` preserved raw ordering and returned the **first 1,200** regions, causing different retained proposal **sets** across repeated calls when >1,200 eligible regions are generated. Example `beach_bird_1379.jpg`: two repeated 1,200-region prefixes had different sorted-coordinate hashes, despite same full 1,508-region raw proposal set. For `beach_bird_1389.jpg`, all 511 eligible regions were retained and their order varied, while their set matched.

The same-bank linear SVM/RBF refitting returned **identical** score arrays and NMS indices; variation is primarily in upstream candidate selection/capping, **not evidence of random classifier training**. This explains why E32/E34/E35 pure-SS baselines of 14.3370%, 14.3370% and 13.4752% cannot be compared across independent workflow runs as if the proposal bank were identical, even with shared seeds/images. These results are still useful as *paired within-run* experiments but require a stable proposal cap and re-evaluation for strict cross-run reproducibility.

**Critical handling:** At the time of this audit, two already launched E33 full-test GitHub workflows were observed: [43828726227](https://github.com/notevensmart/COMP9517_bird_detection/actions/runs/43828726227) and [43830283187](https://github.com/notevensmart/COMP9517_bird_detection/actions/runs/43830283187), both using pre-existing checkout snapshots. Do **not** select whichever TEST score is higher. Treat the first fully valid frozen model result as the primary final evaluation and any concurrent duplicate as a consistency audit; report code SHA and differences transparently. Since the old cap is nondeterministic, future models must sort and cap deterministically *using TRAIN/VAL-only development*, then revalidate before any further TEST usage. No TEST-based model tuning is permitted.
